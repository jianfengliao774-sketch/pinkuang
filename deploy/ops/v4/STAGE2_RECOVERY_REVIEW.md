# Stage 2 finalized failure recovery candidate

This is isolated source for review. `BEMINE_FRESH_STAGE2_HOLD` remains enabled by default; this branch does not authorize a hardware-wallet action or a production deployment. No Stage 2 recovery path simulates or broadcasts a transaction.

A failed Authority creation or any of the six later Authority actions may be recovered only after a finalized failed receipt or finalized same-nonce replacement/cancellation. An unknown winner, pending receipt, mismatched fee, uncertain nonce or changed transaction data blocks recovery. The failed creation additionally requires the exact reviewed creation artifact and no code at its original nonce's predicted CREATE address at finalized and latest blocks. The server proves each parent-hash link from every archived winner to one common finalized/latest chain. It also links refreshed finalized and latest tags and rechecks state if either advances.

The 48-hour Timelock is the minimum delay for later scheduled governance actions, not a waiting period between these seven direct Stage 2 transactions. Hardware-wallet confirmations can still be separated by days. Both browser and server therefore verify long gaps as continuous 4,096-header segments, fetching at most 128 headers concurrently. The parent hash at each verified segment boundary is the next segment's checkpoint; no block-number or hash comparison skips intervening headers. A one-million-block total ceiling bounds each request and fails closed if exceeded. Long proofs may take time or hit RPC limits; an unavailable proof never releases a new signature.

Both browser and server check the completed role prefix at finalized and latest: both Factory proxy and implementation code hashes, EIP-1967 implementation slots, owner/operator/treasury, market bindings, empty pools, 48-hour Timelock delay and hardware-wallet proposer/canceller rights, plus the Authority's reviewed runtime code, CREATE address and fixed bindings after it exists. Server `eth_call` requests carry `blockTag` inside the ethers transaction object so finalized and latest role reads actually reach their intended blocks. After refreshed state reads, the server rechecks every winner block and both original and refreshed anchors to catch a reorg during those reads. The server repeats its check before accepting a new signing intent, including every archived same-nonce winner and its original finalized anchor. The browser repeats its chain and state checks immediately before the hardware-wallet request.

The revision-guarded recovery operation archives the original attempt, winning hash, receipt, fee and finalized anchor into immutable `attempts[]`; the next state is `waiting` for the **same action**. Its fee remains in `spentWei`. A later transaction needs a separate manual click and a fresh nonce. Normal journal PUT cannot erase or rewrite archived attempts.

Local tests cover failed and replaced step 1, failed step 3, replaced step 7, held first-step CREATE address, latest-role and implementation drift, inconsistent ancestry, unknown winner, stale revision, server revalidation on a later signing intent, and the disposable 16+7 Anvil success flow. The local chain run is not a BSC production rehearsal. Before any Stage 2 unfreeze, review this branch and a fresh release package, verify the isolated original-Gas-wallet attestor in its actual unit, confirm the fresh Stage 1 graph and wallet on the finalized chain, and rehearse the recovery path on a disposable fork. Keep v4 relay and product senders disabled while v2 continues under its own policy.
