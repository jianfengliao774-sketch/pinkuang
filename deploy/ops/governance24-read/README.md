# Isolated governance24 read service

These are reviewed deployment templates, not an installer. No server or production configuration was changed by this code task. This service adds only `/pinkuang-governance24-read/api/rpc` on loopback `127.0.0.1:4230`; it does not replace the existing Firsto/target-owner or product services. The new governance24 static release pins this exact same-origin endpoint during preparation, build and packaging.

The standard guarded proxy remains unchanged and handles its prior read-only methods, including code/storage/calls, block headers, transaction counts, transactions and receipts. Full block transaction requests and all wallet/write/debug methods remain rejected. Its state/code/header reads use the protected archive destination; its transaction body/receipt reads use the separately proven transaction destination. Product/index fallbacks are not configured here. The server exposes no index, journal, static asset or signing route.

The new log handler accepts only `eth_getLogs` for old timelock `0x2c0AaE63302A7bF7caF5322Cdfc9da67d4ec8F97`, with `CallScheduled(bytes32,uint256,address,uint256,bytes,bytes32,uint256)` topic `0x4cf4410cc57040e44862ef0f45f3dd5a5e02db8eb8add648d4b0e236f1d07dca`. Requests require explicit canonical numeric from/to blocks after the independent review anchor, contain at most 2048 blocks inclusive, and end no later than the archive's finalized head. Optional indexed operation-ID and call-index topics may be scalar 32-byte hashes or null; OR arrays, address arrays, other events/contracts, wildcard event signatures and blockHash filters are rejected.

Every log read proves BSC chain ID, reads the finalized header, obtains the complete bounded log response, then rechecks that exact header and BSC chain ID. The handler rejects removed, duplicate, unrelated or malformed rows, wrong response IDs, RPC refusals, redirects and oversized responses; it never truncates or filters a bad response into success. No log cache or fallback is used. Four concurrent log requests globally and two per client are allowed, with 100ms between archive request starts and no unbounded wait queue; each request has one 13-second deadline and a 1MiB response ceiling. The proof module independently reconciles the full initial inventory with these incremental events and canonical timestamps, so an empty or failed log query cannot excuse a new pending operation. State is read-only; requests cannot choose an upstream URL.

Deploy into a new versioned directory beneath `/srv/pinkuang-governance24-read/releases/`, and select its independent `current` symlink. Required runtime files are `deploy/server/governance24-read/{governance24-read-server,scheduled-logs}.mjs` and the unchanged `deploy/server/upgrade-read/{live-data-proxy,request-limiter}.mjs`. All use Node built-ins; no wallet library, key or signer is loaded. Use the existing pinned Node 24 runtime and the verified existing unprivileged `www-data` account with read access to these files. Review the unit's Node path and service account for the target host before installing this new unit.

Create `/etc/pinkuang-governance24-read.env` locally on the target host, root-owned mode 0600, with values from its protected RPC configuration. Do not place the protected URLs into this repository, public static files, command arguments or logs. This file must define:

```text
GOVERNANCE24_READ_PORT=4230
GOVERNANCE24_REVIEW_ANCHOR_BLOCK=126156767
GOVERNANCE24_READ_RPC_URL=<protected archive RPC URL>
GOVERNANCE24_READ_TRANSACTION_RPC_URL=<separate transaction/receipt RPC URL>
```

Existing `BEMINE_READ_*`/index environment variables do not populate this service. Both RPC destinations must be HTTP(S), distinct and free of URL userinfo/fragments. The log contract/topic and initial reviewed anchor 126156767 are source-owned constants; the environment must match the anchor exactly. Rebuild the static release only after its final independent roots and this reviewed anchor are ready; changing the anchor requires matching reviewed release inputs and source review. The integrated release fills independently reviewed roots after the complete canonical inventory and fork rehearsals. The governance24 UI allows up to ten minutes for the complete incremental read-only preflight, while each HTTP request still has its existing 15-second limit and account/epoch abort protection. This longer read budget neither requests a signature nor retries a wallet transaction.

Copy the new systemd unit and include the new nginx snippet within the existing HTTPS server. The snippet maps only the exact new API route to port 4230, overwrites `X-Real-IP`, caps request bodies at 64KiB, disables caching, and rejects other routes under the new prefix. Validate the unit and `nginx -t` before starting the new service and reloading nginx. Leave existing services and routes in place. Confirm a chain-ID read returns `0x38`; verify a one-block valid scoped log request above the pinned anchor returns the expected canonical result; verify writes, other log events, excessive ranges and requests at/below the anchor fail. Never use a wallet send for these checks.

The independent service can be rolled back by removing only this nginx include and stopping only `pinkuang-governance24-read.service`. Because the governance24 UI now requires this route, pause publication of that entry while its read service is unavailable. Existing Firsto/product routes remain independent.

Local tests (no production RPC): `node --test deploy/server/governance24-read/governance24-read-server.test.mjs`. The integration harness uses loopback HTTP plus deterministic upstream responses and tests ordinary reads, scope/range/canonical checks, response failure modes, bounded concurrency and refusal of all write/other routes.
