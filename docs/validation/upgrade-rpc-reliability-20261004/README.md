# Standalone upgrade read RPC reliability — 2026-10-04

The standalone TargetOwner upgrade page uses a dedicated, loopback-only read service on port 4228. Its public `/pinkuang-target-owner-upgrade/api/rpc` route is the only route switched to that service. The service exposes only `/api/rpc`; it has no journal, index, static or wallet-write handler. Product and deployment read services retain their own configuration.

Only `eth_getTransactionByHash` and `eth_getTransactionReceipt` use the separately configured transaction read node. That node must pass a strict, short-lived BSC chain-ID proof before each lookup, including JSON-RPC version, exact request ID and response shape. Its errors, wrong chain, malformed replies and in-flight identity changes fail closed without another node or a cached transaction answer. Block headers, finalized/canonical checks, `eth_call`, `eth_getCode` and `eth_getStorageAt` stay on the archive node. The secondary node's chain ID alone does not certify a receipt: the existing client still verifies its canonical block against the archive-backed public proof.

Archive reads may retry **once** on the same node after 1.1 seconds, and recheck chain ID before repeating a data read. This applies only to a valid, matching JSON-RPC `-32005` error explicitly identifying per-second CUPS capacity, or a non-RPC HTTP 429/502/503/504 gateway response. Monthly credit exhaustion, other JSON-RPC errors, malformed envelopes, mismatched IDs and ambiguous response bodies do not retry. Diagnostics record method, HTTP status, standard JSON-RPC field presence, ID type/match, error code and a fixed category; they omit parameters, response bytes, error messages and endpoint URLs. The new service limits upstream work to four concurrent reads and two per client.

Source commit: `86d635e452cba857e820108c7218b8fc3cd5d237`. Focused server tests: 62 passed, zero failed; JavaScript syntax and Git whitespace checks passed. Tests cover route isolation, provider selection, wrong-chain and malformed-response rejection, pending-to-mined receipts, no fallback or write methods, bounded retry and no retry on monthly/ambiguous errors.

Publication changed the single upgrade RPC nginx location from the existing product read service on port 4227 to the new loopback service on port 4228 at **2026-10-04 16:39 CST**. The eight existing services, formal frontend, standalone upgrade static files and other nginx locations retained their recorded identities. [The publication receipt](publication.json) pins the three running source-file hashes and the dedicated systemd unit hash; [source-pins.json](source-pins.json) records the matching commit files.

The earlier public prepared proof failed on `eth_getCode` with HTTP 502 after 4.739 seconds ([before-proof.json](before-proof.json)). After the switch, the same complete prepared-phase proof passed on the dedicated loopback service in 18.070 seconds and through the public upgrade route in **15.261 seconds**, with `baselineVerified: true` at BSC block 125645785 and zero failures. The public proof made 34 chain-ID, 6 block-header, 24 code, 4 storage and 26 call reads ([local-proof.json](local-proof.json), [public-proof.json](public-proof.json)).

An independent genesis transaction check read the exact transaction, receipt and canonical block, found its hash at transaction index 23 with successful receipt status, and confirmed the block was below the finalized head. It passed locally in 2.202 seconds and publicly in **2.677 seconds** ([local-receipt-proof.json](local-receipt-proof.json), [public-receipt-proof.json](public-receipt-proof.json)). This verifies the historical genesis read path; it is not evidence that a new upgrade transaction was signed or deployed. A public page reload showed no 502, but the user must still approve the actual wallet requests to advance the upgrade.

The original archive 502 did not include a captured upstream response shape, so its cause is unproven. The bounded retry handles only the explicit cases described above and continues to reject ambiguous errors. [probe.mjs](probe.mjs) and [receipt-probe.mjs](receipt-probe.mjs) reproduce the read checks; they reference the operator's local release path and take the endpoint as an argument. [publish.py](publish.py) documents the guarded service and one-location publication, without endpoint values or credentials. No wallet signing, broadcasting or contract upgrade was performed for this read-service release.
