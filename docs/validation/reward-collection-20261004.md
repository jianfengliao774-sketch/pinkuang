# Loaded single-miner collection and claims

The formal Rewards page previously required opening a separate action for every pool and currency. It now offers Collect, Claim, and Collect and claim controls for the already loaded single-miner positions. More positions must be loaded before starting; portfolio projects and market proceeds retain their separate claim controls.

These controls start a serial wallet workflow, not an intermediary contract. Every call is a zero-BNB call from the current holder to the verified PoolVault. The existing contracts settle claims by `msg.sender`, so each call still requires wallet confirmation. No contract deployment or upgrade is part of this release.

Each pool is checked against the reviewed Factory at a canonical block. Current state and shares decide harvest eligibility; cached Funding or Active labels cannot authorize or exclude a current payout. After a harvest receipt is confirmed, the workflow rereads balances at or after its block before issuing a positive BEM claim. BNB is withdrawn only when the freshly read owed amount is positive. Zero-share historical credits remain eligible. Collection can produce no new output and still consume Gas, so a confirmed call is never described as proof of new income. A known transaction revert is recorded, and independently booked balances can still be claimed. Unsettled refunds and uncollected portfolio children are outside this workflow.

The whole run holds the existing submission lock. Wallet, chain, page, deployment or component lifetime changes stop later sends. Every wallet intent is durably saved before opening the wallet. Unknown submission responses, pending receipts and unavailable reads pause instead of resending. Recovery verifies the exact wallet, pool, no-argument selector, zero value, chain, hash, canonical receipt and a block strictly after the pre-send balance snapshot. An old receipt cannot remove a different tab's newer pending intent. Recovery never continues the queue automatically.

Reads happen only for this explicit action and the current transaction. The workflow does not request Firsto prices, scan the market, log into the journal, estimate Gas or simulate transactions. While it waits for a receipt, the ordinary member receipt loop is suspended to avoid polling the same hash twice. Confirmed block numbers are serialized as strings before saving member history.

Validation uses offline ABI fixtures, fake wallets and injected RPC replies. It covers zero balances, zero-share credits, current state changes, harvest/claim reverts, pending receipts, rejection, stale blocks, identity changes, durable lost-response recovery and cross-tab lock protection. Production publication evidence is recorded separately after build verification.
