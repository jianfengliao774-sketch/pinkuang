# External target transfer and subscription linkage

Latest public-catalog revision (2026-10-04): confirmed unavailable fixed targets are hidden from every public project catalog, including the project Overview tab, search results and loaded-project counts. Personal positions, existing detail addresses and withdrawal entries retain the real state and balances. This supersedes the earlier public historical-project group described below; no contract state or refund timing changes with this frontend revision.

When an external buyer acquired a fixed fundraising target, the site previously continued to show the project in Funding and build deposit calldata. Invalid sell orders were rejected only when procurement ran; a fully funded pool still had to wait for its purchase deadline before recording refunds.

The read-only index now tracks only Funding/Funded single-miner targets. It reconstructs the owner at the Factory's PoolCreated event from the creation-block end state and ordered ERC721 Transfers. This also covers an external purchase later in the same block. Historical owner and purchase mode are persisted under their canonical block hash. A changed owner, other than the pool itself, makes a fixed project unavailable for new website subscriptions. An opt-in flexible project's reference miner is not treated as a binding target.

The Funding directory excludes confirmed unavailable targets while Overview, personal positions, detail routes and existing withdrawal entries retain the real contract state and all balances. Unknown or timed-out evidence is not described as a sale and does not delete a project. It blocks new website subscriptions until the check succeeds. The selected target is checked against current on-chain ownership both while preparing a subscription and again immediately before opening the wallet.

This website/index release does not change the deployed contract, sign a pause or transfer funds. A direct call to the existing Vault can still bypass the website restriction. Existing Funding subscribers retain withdrawDeposit followed by withdrawBnb. Existing Funded pools retain their purchase-deadline finalizeFailure and pull-payment withdrawal. Early permissionless refunds and atomic deposit rejection require a separate reviewed Beacon implementation upgrade; candidate code is not represented as already active.

No paid RPC is launched by a display HTTP request. First initialization reads the historical mode and owner, using the already configured archive-capable logs endpoint only when public historical reads fail, with chain ID and historical block hash checks. Transfer logs are batched by collection/creation block. Afterwards each fixed fundraising target adds at most one public ownerOf read per new indexed block; a repeated materialization of that same block reuses its successful result. Flexible, active and portfolio-child targets add no ownership polling. Failed reads remain retryable.

Offline validation: the full web suite passed 1,089 tests; catalog, price/review checks and JSX parsing passed. The full chain-index suite passed 141 tests and the index publisher passed six offline success/rollback checks. Backend tests cover ordered same-block transfers, unknown data, archive endpoint identity, reorganizations, restart persistence, shared public/account rows, and no display-request RPC fan-out. Production publication evidence is added after verifying the new shared cache and static release.
