# Member wallet operations remain independent of worker readiness

On 2026-09-30 the formal Funding pool `0xC0EdD7E9Ef4eba0f75Cf85a14F35fe4F7190686e` had 100 remaining shares, `trusted=true`, `depositPaused=false` and an unexpired funding deadline. Its subscribe button was disabled because the product's combined `operationalReady` was false. The mining supervisor had exited after finding an unresolved transaction in a different pool's shared Gas wallet journal. The index was complete and the current deployment graph was verified.

Ordinary member-wallet calls now use the verified formal deployment independently of purchase/mining service liveness. Browser and journal share an explicit target-type/function/value policy for deposits, share-market operations, member claims, transfers and sale governance. Factory/Authority forwarding, automatic mining and procurement are outside this policy. The actual registered target, canonical calldata and exact amount remain verified before submitting; the existing application path does not run transaction simulation or dynamic Gas estimation.

A verified Funding preview remains available while its display snapshot is cached or reloading. Preparing the action reads its actual current pool state and exact payable amount. A background refresh no longer revokes the preview merely because its account display is temporarily reloading. Changed route/pool identity, an actually paused/full pool and an active wallet request remain distinct. Boot configuration has stable React identity so unrelated renders cannot continuously restart pending receipt polling.

The mining supervisor checks whether a pool needs work before competing for the shared Gas wallet. Ordinary wallet contention or a transaction waiting for its receipt keeps the supervisor running and preserves the original transaction journal and nonce. It does not rebroadcast or renew a readiness heartbeat for an incomplete scan. Subsequent healthy scans renew readiness. Corrupt journals and deployment/identity errors remain errors.

Regression coverage includes the real fresh-configuration loader with all worker gates false, the cached Funding preview, exact payable calldata, wrong deployment/target/value rejection, a real temporary cross-pool wallet pointer/lock, receipt-only reconciliation over repeated scans, Funding pools avoiding the wallet lock, and fatal binding/journal errors. Tests never send a financial transaction.
